## Why this matters

`package.json` carries security-motivated version pins that are **silently ignored**: they live under `"pnpm": { "overrides": ... }` (and a typo'd `"pbun"` key), but this repo installs with Bun, which reads neither. Proof: the pin demands `undici >= 5.28.5`, yet `bun.lock` still resolves `undici@5.28.4` (under `@vercel/node`). Separately, `bun audit` reports advisories on packages reachable at runtime, and three dependencies are dead weight installed on every CI run: `notion-client` and `notion-utils` (zero imports anywhere in `src/`, `vendor/`, or `scripts/` — the codebase uses `@notionhq/client` exclusively) and `astro-mcp` (not registered in `astro.config.ts` integrations, no references in source).

## Current state

- `package.json` lines 7–22 (verbatim, as of `43a2df2`):

  ```json
  "pnpm": {
    "overrides": {
      "undici": ">=5.28.5",
      "esbuild": ">=0.25.0"
    }
  },
  "engines": {
    "node": "22.x"
  },
  "pbun": {
    "overrides": {
      "path-match": "bun:path-to-regexp@^6.2.1",
      "undici": "^6.21.0",
      "esbuild": "^0.25.0"
    }
  },
  ```

- `bun.lock` — `@vercel/node@5.7.3` pins `"undici": "5.28.4"` (vulnerable line; the ignored override wanted ≥5.28.5). `@vercel/blob@2.3.0` wants `undici ^6.23.0`. Both `vercel` (the CLI, a devDependency) and runtime paths resolve through this lockfile.
- Dead deps, verified by grep at planning time:
  - `grep -rln "notion-client\|notion-utils" src vendor scripts` → no matches (`notion-client@^7.10.0`, `notion-utils@^7.10.0` in `dependencies`).
  - `grep -rn "astro-mcp" src scripts astro.config.ts` → no matches (`astro-mcp@^0.4.2` in `dependencies`).
- Bun override mechanism: Bun honors a **top-level** `"overrides"` key in `package.json` (npm-style, name → version range). It does not read `pnpm.overrides`.
- An audit run at planning time flagged, among ~137 mostly build-time advisories, these as reachable-relevant: `undici` (via Vercel packages), `form-data < 4.0.6` (via `@notionhq/client → @types/node-fetch → form-data`). Re-verify with a fresh `bun audit` — do not trust this list blindly.

## Steps

### Step 1: Record the baseline

Run `bun audit` and save the summary counts (total/critical/high) somewhere you can quote in your final report. Run `bun run build` once to confirm the tree builds BEFORE any change (if it doesn't, STOP — pre-existing breakage).

**Verify**: `bun run build` → exit 0.

### Step 2: Consolidate the override keys

In `package.json`: delete the entire `"pbun"` block (typo, read by nothing) and the `"pnpm"` block, and add a top-level:

```json
"overrides": {
  "undici": ">=5.28.5",
  "esbuild": ">=0.25.0",
  "form-data": ">=4.0.6"
}
```

(Drop the `path-match` entry from the old `pbun` block — it referenced a `bun:` protocol in a key nothing ever read; if `bun audit` in Step 1 flagged `path-match`/`path-to-regexp` as reachable, note it in your report instead of guessing a pin.)

Run `bun install` to re-lock.

**Verify**: `grep -c '"pbun"\|"pnpm"' package.json` → 0; `bun install` → exit 0.

### Step 3: Confirm the overrides actually took effect

**Verify**: `grep -n '"undici@5.28.4"\|undici@5.28.4' bun.lock` → no matches, and `grep -n 'form-data@4\.0\.[0-5]"' bun.lock` → no matches. If `undici@5.28.4` is still present, Bun did not apply the override — STOP and report (include your Bun version from `bun --version`).

Then: `bun run build` → exit 0, and `CI=1 bun run test:e2e` → exit 0. The build exercises the Vercel adapter and Notion loader paths that undici/form-data sit under.

### Step 4: Remove the dead dependencies

First re-verify each is truly unused (the situation may have drifted):

- `grep -rln "notion-client" src vendor scripts` → must be empty
- `grep -rln "notion-utils" src vendor scripts` → must be empty
- `grep -rn "astro-mcp" src scripts astro.config.ts` → must be empty

If all empty: remove `notion-client`, `notion-utils`, and `astro-mcp` from `dependencies` in `package.json`, then `bun install`.

**Verify**: `bun run build` → exit 0; `bun run typecheck` → exit 0.

### Step 5: Re-audit and record the delta

Run `bun audit` again. Record before/after counts in your final report. Do NOT chase the remaining advisories in this plan — most are build-time-only ReDoS-class noise; anything that looks runtime-reachable goes into your report as a note for the maintainer.

**Verify**: `bun audit` runs; `CI=1 bun run test:e2e` → exit 0.
